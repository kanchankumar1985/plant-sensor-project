1. Executive Summary

The Plant Sensor Project is an end-to-end Internet of Things (IoT) plant monitoring and interactive care system. It combines an ESP32 microcontroller, environmental sensors, a capacitive touch sensor, a peristaltic pump, computer vision, and a local Vision-Language Model (VLM) to monitor a plant and react to human touch.

The core workflow is: the ESP32 continuously streams temperature and humidity data over USB serial. When a person touches the sensor, the system captures a webcam image, records a short video, runs YOLO person detection, optionally activates the pump when a person is detected, saves all media and metadata to a TimescaleDB time-series database, and queues a VLM analysis to describe the scene and plant health.

A FastAPI backend exposes REST endpoints and static media, while a React plus Vite dashboard visualizes live sensor data, historical charts, snapshots, video clips, AI analysis, and system logs.

All runtime data and logs can be stored on an externally mounted SD card to save laptop storage.

2. The Idea Behind the Project

The project explores three ideas in one device:

  • Always-on plant telemetry: Track temperature and humidity around the plant over time and detect anomalies.
  • Human-plant interaction: Use a touch sensor as a trigger. When a person touches the plant area, the system responds with audio feedback, captures what the camera sees, and decides whether to run the pump.
  • Local AI reasoning: Instead of relying on the cloud, a local Ollama instance running the LLaVA vision model analyzes images and videos to detect people, describe clothing, assess plant health, identify yellowing, drooping, or wilting, and estimate image quality.

In the current demonstration configuration, the pump is activated when a person is detected in the image. This is controlled by the TouchWorkflowOrchestrator and the command PUMP_ON_YELLOW_LEAVES. The same VLM pipeline can later be switched to trigger on plant conditions such as yellow leaves, making the system a closed-loop plant-care assistant.

4. High-Level Architecture

The system is organized in four layers: hardware/firmware, data ingestion and orchestration, AI and storage, and the web dashboard. The hardware layer streams data over USB serial. The ingestion layer parses, persists, and triggers actions. The AI layer adds person detection and VLM reasoning. The storage layer keeps time-series and media metadata. The dashboard queries the REST API to present data to the user.

5. Hardware and Firmware Layer

The physical device is built around an ESP32 Dev Board. A capacitive touch sensor is wired to GPIO4 and debounced in firmware. The HDC302x temperature and humidity sensor connects to the default ESP32 I2C pins: SDA on GPIO21 and SCL on GPIO22. A peristaltic pump is driven through a relay pin, and two LEDs indicate touch and temperature states. The ESP32 communicates with the host over USB at 115200 baud.

The main production firmware is plant-monitor/esp32/touch_sensor/touch_sensor.ino. Additional prototype and test sketches live in the repository root, such as touch_sensor/, touch_sensor_led_pump/, touch_sensor_led_pump_unified/, touch_led_control/, and touch_sensor_test/. These were used to develop and isolate each subsystem before unification.

The unified firmware outputs two kinds of serial traffic:

  • Plain-text lines TOUCHED and NOT_TOUCHED for touch events.
  • JSON objects with fields device_id, temperature_c, humidity_pct, and led_state for periodic environmental readings.

The ESP32 also accepts the command PUMP_ON_YELLOW_LEAVES over the same serial link. On receipt, it turns the pump on for approximately 2 seconds and then enforces a 60-second cooldown before the next activation.

6. Serial Communication and Data Ingestion

The serial layer is the bridge between the ESP32 and the rest of the system. The primary process is serial_unified_listener.py, which:

  • Scans for an ESP32 on /dev/cu.usbserial-0001 and reconnects automatically if the port drops.
  • Reads each serial line, distinguishes touch text from JSON sensor data, and keeps a reference to the serial port for downstream pump commands.
  • Calls insert_touch_event() to write TOUCHED and NOT_TOUCHED events into the touch_events table with a timestamp and device ID.
  • Calls parse_sensor_data() and insert_sensor_reading() to store temperature, humidity, and LED state in sensor_readings.
  • Checks temperature thresholds and can trigger optional video recording.
  • On touch, calls handle_touch_event(), which delegates to the TouchWorkflowOrchestrator running in a background thread.

Two older dedicated listeners, serial_reader.py and serial_touch_listener.py, still exist for testing and debugging but the unified listener is the preferred runtime path.

7. Continuous Monitoring and Alerts

Outside of touch events, the system continuously monitors the plant environment. The ESP32 sends a JSON reading at a regular interval. The unified listener inserts it and can trigger a temperature alert when the configured threshold is reached. The temperature threshold and snapshot cooldown are controlled through environment variables such as SNAPSHOT_COOLDOWN and VIDEO_ALERT_* values.

React polls the /api/readings/recent and /api/readings/latest endpoints every few seconds, maps the data onto Recharts line charts, and displays the latest temperature, humidity, device ID, and last update time. The dashboard supports live mode with auto-refresh and custom time range queries.

8. Touch-Triggered Workflow

Touch is the main human interaction. When the firmware reports TOUCHED, the unified listener stores the event and starts the TouchWorkflowOrchestrator. The orchestrator runs the following steps in a background thread so the serial listener never blocks:

  1. Text-to-speech: The tts_service.py calls the macOS say command to announce "Sensor touched".
  2. Snapshot: capture_webcam_image() opens the webcam, applies exposure and brightness settings, captures a frame, and saves a JPEG file.
  3. Video clip: record_video_alert(duration=3, fps=10) records a short MP4 clip by first writing an MJPG AVI and then converting it with ffmpeg.
  4. YOLO person detection: detect_person.py loads the yolov8n.pt model, detects people, draws bounding boxes, and saves a boxed image and JSON metadata.
  5. Pump decision: If a person is detected, the orchestrator sends PUMP_ON_YELLOW_LEAVES through the serial port with retry logic. Otherwise the pump stays off.
  6. Database insert: capture_with_vlm.py or the orchestrator calls insert_snapshot_quick() to write the snapshot row including image path, video path, YOLO metadata, and an analysis_status of queued.

9. Pump Decision Logic

The pump is controlled by the result of YOLO detection. The _trigger_pump() method in services/touch_workflow.py checks that the serial port is open, retries up to six times if the port is transiently unavailable, and then sends the PUMP_ON_YELLOW_LEAVES command followed by a flush. The ESP32 firmware handles the actual 2-second pump run and 60-second cooldown.

This behavior is currently configured for person-detection-based triggering as a demonstration. It can be extended to use VLM plant-health results by changing the condition that calls _trigger_pump().

10. Computer Vision and AI Layer

The AI layer has two stages: fast local object detection and slower vision-language reasoning.

  • YOLOv8n: The detect_person.py module uses the pretrained yolov8n.pt model from Ultralytics to detect people. It returns person_detected, person_count, a list of bounding boxes, and saves a boxed image for the UI.
  • Ollama VLM: The vlm.ollama_client.py module connects to a local Ollama server at OLLAMA_HOST (default http://localhost:11434) using the llava:7b model. It base64-encodes an image, posts to /api/generate, and requests JSON output when VLM_FORCE_JSON is enabled.
  • VLM analyzer: vlm.vlm_analyzer.py resizes the image for faster inference, selects a prompt, calls Ollama, and parses the returned JSON or extracts JSON from free text.
  • Analysis rules: vlm.analysis_rules.py normalizes the VLM output and computes an enhanced dictionary with flags such as plant_visible, yellowing_visible, drooping_visible, wilting_visible, image_quality, and reliability.
  • VLM worker: vlm_worker.py runs as a background daemon. It polls the plant_snapshots table for rows with analysis_status = 'queued', claims the oldest one, runs analyze_image_with_vlm(), and updates the database with the results and analysis_status = 'completed' or failed.

12. React Frontend Dashboard

The frontend is a React single-page application built with Vite. It fetches data from the FastAPI backend at http://localhost:8000 and renders several focused cards.

  • App.jsx: Main layout, state for live/historical mode, date range picker, and fast-preset buttons (last 5 minutes, 15 minutes, 1 hour, today).
  • PlantHealthCard: Displays the latest VLM plant health assessment and warning flags (yellowing, drooping, wilting).
  • PlantSnapshot: Shows the most recent captured image with temperature and humidity overlay.
  • SnapshotGrid: Gallery of recent snapshots with thumbnails, video badges, and click-to-detail behavior.
  • PersonDetection: Highlights person detection metadata and boxed images.
  • AIAnalysisCard / VideoAnalysisCard: Display VLM image and video analysis summaries.
  • AIStatusCard: Shows Ollama connection, model name, queue status, and error counts.
  • TouchStatusCard: Displays the latest touch state and seconds since last touch.
  • LogsPanel: Auto-refreshing log viewer with level coloring, live indicator, and pause/resume controls.

Recharts is used for the temperature and humidity line chart. The dashboard uses CSS-in-JS styling and fetches images, boxed images, and videos through the FastAPI static and video endpoints.

13. Logging and Storage

Centralized logging is managed by logging_config.py. It creates rotating file handlers for each component and can mirror logs to the console. Log files are stored under the directory pointed to by LOGS_DIR. If an SD card is mounted at /Volumes/SD-128GB/PlantMonitor and writable, the start scripts set LOGS_DIR, IMAGES_DIR, and VIDEOS_DIR to that location. Otherwise they fall back to local backend/logs, backend/images, and backend/videos.

The Logs API in routes/logs.py lets the frontend and operators retrieve the latest lines, list log files, read an entire file, and get aggregate statistics. Typical loggers include app, api, serial_reader, camera, and vlm.

15. Error Handling and Resilience

The system is designed to degrade gracefully when parts of the pipeline are unavailable.

  • Serial port: The unified listener reconnects automatically if the port disappears, and the orchestrator retries pump commands up to six times when the port is transiently closed.
  • Database: Each DB operation is wrapped in error handling with rollback. Sensor insert failures are logged but do not crash the listener.
  • Camera: Capture failures are logged and skipped; the workflow continues to YOLO if an image is unavailable, then falls back to no detection.
  • YOLO: If the model or Ultralytics is not available, the module returns person_detected = false so the workflow can still complete.
  • VLM: If Ollama is offline, the worker marks jobs as failed with analysis_error. The system continues to capture and queue new snapshots for later analysis.
  • SD card: Scripts fall back to local directories when the SD card path is not present or not writable.
